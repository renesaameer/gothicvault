# /database — Portable Supabase setup

One folder, one SQL file, zero manual dashboard clicks.

## TL;DR — Install on a fresh project

1. Create a new Supabase project (or remix this app — connection is automatic).
2. Open **SQL Editor → New query**.
3. Paste the entire contents of [`full_setup.sql`](./full_setup.sql) and click **Run**.
4. Done. Visit `/admin/login`; the first signup automatically claims the `admin` role.

The script is fully idempotent — re-running it is safe and never duplicates data.

## What it installs

| Section | File | Contents |
|---|---|---|
| Extensions & enums | `01_extensions.sql` | `pgcrypto`, `app_role` enum |
| Schema | `02_schema.sql` | 37 tables + indexes (auth, catalog, commerce, content, settings) |
| Functions | `03_functions.sql` | 11 helpers + RPCs (`has_role`, `is_admin_or_staff`, `track_order`, …) |
| Triggers | `04_triggers.sql` | `on_auth_user_created`, `set_updated_at` on mutable tables |
| RLS policies | `05_policies.sql` | Public-read where appropriate, `is_admin_or_staff` for writes |
| Storage | `06_storage.sql` | `media` bucket (public read, staff write) + object policies |
| Default settings | `07_defaults.sql` | Singleton rows for shop/footer/contact/design/invoice/etc. |
| Demo catalog | `08_seed.sql` | 3 categories, 1 brand, 2 delivery zones, 6 SPEOS products |

`full_setup.sql` is the concatenation of all eight numbered files with banners. It is regenerated by `npm run db:build` — do not edit it by hand.

## npm scripts

```bash
npm run db:build    # Rebuild full_setup.sql from the 0N_*.sql parts
npm run db:verify   # Compare live DB against manifest.json (needs SUPABASE_DB_URL)
npm run db:export   # Dump current schema to database/_exported_schema.sql (needs pg_dump)
```

`db:verify` and `db:export` need `SUPABASE_DB_URL` in `.env` — see `.env.example`.

## Reset the database

Supabase has no one-click reset. Easiest path:

1. Project Settings → **General** → **Pause project**, then create a new one.
2. Or run this in SQL Editor to wipe the public schema, then re-run `full_setup.sql`:

```sql
drop schema public cascade;
create schema public;
grant usage on schema public to anon, authenticated;
```

Storage objects in the `media` bucket must be deleted manually from Storage UI.

## Adding new tables / migrations

1. Edit the relevant `0N_*.sql` file (schema goes in `02_schema.sql`, policies in `05_policies.sql`, etc.). Keep statements idempotent: `create … if not exists`, `drop policy if exists` before `create policy`, `on conflict do nothing` on seeds.
2. Update `manifest.json` if you added a table/function/bucket.
3. Run `npm run db:build` to regenerate `full_setup.sql`.
4. Run the new SQL on existing Supabase projects via the SQL Editor (or, on Lovable, via a migration in `supabase/migrations/`).

## Troubleshooting

| Symptom | Fix |
|---|---|
| `relation "user_roles" does not exist` when running policies | The script files were run out of order — always use `full_setup.sql`, not individual parts. |
| "new row violates RLS on `user_roles`" on first login | Another account already claimed admin. Have an existing admin assign your role at `/admin/roles`. |
| Image uploads fail | Re-run `full_setup.sql`; verify the `media` bucket exists and is public in **Storage**. |
| Edge function 401 | Always invoke via `supabase.functions.invoke()` so auth headers attach. |
| `db:verify` says "missing table" but the table exists | Refresh local manifest: `npm run db:build` and edit `manifest.json` if you added new objects. |

## Future-proofing

The numbered layout lets you append new modules without touching old code — for example, when you add subscriptions or multi-tenant SaaS you can introduce `09_subscriptions.sql`, `10_tenants.sql`, etc., and `db:build` will fold them into `full_setup.sql` automatically.
